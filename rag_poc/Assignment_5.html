from nltk.translate.bleu_score import sentence_bleu, SmoothingFunction
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np
import re as _re
import requests as _requests

# Metric 1: BLEU (lexical overlap — do the same words appear?)
def bleu_score(generated, reference):
    """Lexical n-gram overlap. Good for catching factual keyword presence."""
    smoothie = SmoothingFunction().method1
    return sentence_bleu(
        [reference.split()], generated.split(), smoothing_function=smoothie
    )

# Metric 2: Semantic similarity (do they mean the same thing?)
eval_embedder = SentenceTransformer('all-MiniLM-L6-v2')
def semantic_similarity(generated, reference):
    """Embedding cosine similarity. Catches paraphrases BLEU would miss."""
    embs = eval_embedder.encode([generated, reference])
    return cosine_similarity([embs[0]], [embs[1]])[0][0]

# Metric 3: LLM-as-judge — direct vLLM call via /v1/completions
# (matches scripts/a5_experiments/evaluate.py rubric for consistency with
# the ralph_run4 sweep judge scores).
def llm_judge_score(question, generated, reference, chain=None):
    """Gold-based LLM judge (1-5). Calls vLLM /v1/completions directly.

    Parameters
    ----------
    chain : unused. Retained for backwards compatibility with the HF-era
        function signature. The implementation always hits vLLM directly.
    """
    judge_prompt = (
        "[INST] Rate the following answer on a scale of 1 to 5, where:\n"
        "1 = completely wrong or irrelevant\n"
        "2 = partially relevant but mostly incorrect\n"
        "3 = somewhat correct but missing key details\n"
        "4 = mostly correct with minor omissions\n"
        "5 = comprehensive and accurate\n\n"
        f"Question: {question}\n\n"
        f"Reference answer: {reference}\n\n"
        f"Answer to evaluate: {generated}\n\n"
        "Respond with ONLY a single digit (1-5).[/INST]"
    )
    try:
        r = _requests.post(
            "http://localhost:8000/v1/completions",
            json={
                "model": "mistralai/Mistral-Small-24B-Instruct-2501",
                "prompt": judge_prompt,
                "max_tokens": 10,
                "temperature": 0,
            },
            timeout=60,
        )
        text = r.json()["choices"][0]["text"].strip()
        m = _re.search(r"[1-5]", text)
        return int(m.group()) if m else None
    except Exception:
        return None

    """Run a set of chains for one question, return list of result dicts."""
    out = []

        generated = chain.invoke(question)
        out.append({

            'generated': generated, 'gold': entry[gold_key], 'question': question,

    return out

Your 4.1 answer in this text box here. Double click to open.

We use three complementary evaluation metrics because no single metric captures every failure mode in retrieval-augmented generation. BLEU measures lexical overlap and helps check whether key terms and domain-specific language are preserved. Sentence-embedding cosine similarity captures semantic similarity and is better at recognizing paraphrases, but it is less reliable when an answer is semantically close yet factually wrong. LLM-as-a-judge provides a broader assessment of completeness, relevance, coherence, and nuance, though it is also vulnerable to rewarding answers that sound plausible rather than answers that are actually grounded. To ensure topic diversity, we sample every seventh question in the evaluation subset.

To verify that these metrics actually distinguish stronger prompts from weaker ones, we ran a bidirectional validation test with two deliberately degraded prompts: eng_ungrounded, which removed the “ONLY from context” grounding constraint, and mkt_technical, which used technical language for the marketing audience. In the engineering setting, BLEU dropped from 0.088 for eng_v1 to 0.050 for eng_ungrounded, a 42% decline. In the marketing setting, BLEU dropped from 0.128 for mkt_v1 to 0.025 for mkt_technical, an 81% decline. By contrast, semantic similarity fell only slightly, from 0.794 to 0.768 in engineering and from 0.737 to 0.718 in marketing, suggesting that embedding-based similarity is more forgiving. The most important finding is that LLM-as-a-judge behaved unreliably in this setup, scoring degraded prompts higher rather than lower: its score increased from 3.44 to 4.16 in engineering and from 3.40 to 4.40 in marketing. This suggests that when retrieval guardrails are weak, the model may produce ungrounded answers that sound plausible, and LLM-as-a-judge can mistakenly reward style and fluency over factual grounding. Based on these results, BLEU is the strongest primary signal, semantic similarity is a useful supporting metric, and LLM-as-a-judge is included only for completeness with an explicit note that it was unreliable in this experiment.

Pipeline Specifications (5.1.a)¶

Document ingestion and indexing

  • Sources: 32 arXiv papers + 4 Wikipedia queries (8 docs) + 8 web pages = ~48 documents total
  • Chunking: RecursiveCharacterTextSplitter, chunk_size=512, chunk_overlap=32
  • Embedding: multi-qa-mpnet-base-dot-v1 (sentence-transformers, 768-dim)
  • Vector database: Qdrant, persisted on disk, collection rag_tech_db

Retrieval

  • Retriever: QdrantVectorStore.as_retriever(search_kwargs={"k": 8})
  • Top-k: 8 chunks per query
  • Similarity: cosine (default for multi-qa-mpnet-base-dot-v1 dot-product variant)

Generation

  • Primary model: mistralai/Mistral-Small-24B-Instruct-2501 (per assignment constraint)
  • Backend: vLLM 0.19.0 (tensor-parallel across 4× L40S GPUs, dtype float16)
  • Hyperparameters: max_tokens=1000, temperature=0.0 (deterministic for reproducibility)
  • Sweep hyperparameters: temperature=0.0 (for deterministic experiment reproducibility)
  • Secondary model (not used in final): mistralai/Mistral-7B-Instruct-v0.3 (fp16, single GPU)

Why vLLM over HuggingFace pipeline: benchmarked 33x throughput improvement (vLLM: 274 tok/s vs HF Pipeline: 13.8 tok/s for 24B). This made parameter sweeps tractable (75-question eval in ~60 seconds vs ~28 minutes on HF).

Framework: LangChain (chain syntax: retriever | format_docs | prompt | llm | output_parser)

Evaluation

  • Metric 1 (lexical): BLEU via NLTK sentence_bleu with SmoothingFunction.method1
  • Metric 2 (semantic): cosine similarity of sentence embeddings (all-MiniLM-L6-v2)
  • Metric 3 (quality): LLM-as-judge using the same 24B Mistral, 1-5 scale
  • Scoring applied to: 75-question validation set × 2 personas (engineering + marketing)

Persona design: Two prompt templates with distinct system messages direct the SAME retrieved context toward different audiences. The engineering prompt instructs detailed, technical answers grounded in context. The marketing prompt instructs accessible, jargon-free responses for a non-technical audience.

Best config (empirically selected)

  • chunk_size: 512
  • chunk_overlap: 32
  • k: 8
  • embedding_model: multi-qa-mpnet-base-dot-v1
  • model: Mistral-Small-24B (24B parameters, fp16 via vLLM)
  • prompts: eng_v1 / mkt_v1 (details in 5.1.b and 5.1.c)

Final evaluation results (75 validation questions)

  • Engineering: BLEU 0.078, Semantic Sim 0.782, Judge 4.01
  • Marketing: BLEU 0.111, Semantic Sim 0.792, Judge 3.91

(Persona trade-off: engineering emphasizes technical depth leading to higher semantic similarity with gold_answer_research; marketing emphasizes concision leading to higher BLEU with the typically-shorter gold_answer_marketing.)

Retrieval-Augmented Generation (RAG) offers several benefits over traditional language models, particularly in providing reliable and up-to-date answers. Here are the key advantages and how the RAG approach contributes to these improvements:

1. **Factual Accuracy**: RAG enhances factual accuracy by explicitly retrieving relevant passages from a large corpus. This means that the model can ground its responses in up-to-date and contextually relevant information, reducing the likelihood of generating hallucinated or incorrect facts.

2. **Temporal Coverage**: Traditional language models are limited by the knowledge cutoff date of their training data. RAG overcomes this limitation by integrating information from external knowledge bases or search engines, allowing it to provide answers that reflect the most recent information.

This can be beneficial for applications where it is important to understand the source of the generated information.

The RAG approach contributes to these improvements through the following steps:

- **Retrieval**: The model first retrieves relevant passages from an external corpus based on the user's query. This step ensures that the model has access to the most relevant and up-to-date information.

- **Augmentation**: The retrieved information is then used to augment the generation process. This means that the model can incorporate the retrieved information into its responses, enhancing their factual accuracy and relevance.

- **Generation**: Finally, the model generates a response based on the augmented information. This step ensures that the generated response is both contextually relevant and factually accurate.

In summary, RAG's approach of integrating external retrieval with language generation allows it to provide more reliable and up-to-date answers compared to traditional language models. QUESTION:

5.3.d. What was your design philosophy of the prompts? How did they differ between engineering and marketing support?

==== ENTER YOUR 5.3.d. ANSWER IN THIS TEXT BLOCK. Double click to open.

The prompt design was built around three core dimensions:

Persona Framing defined who the model was speaking to (eng_v1 vs mkt_v1). Engineering prompts were framed around a technical audience expecting depth, precision, and implementation-level detail. Marketing prompts were framed around a business audience expecting actionable, outcome-oriented responses. This framing was the primary driver of tone and response structure.

Grounding Constraint controlled where the model was allowed to source its answers. The core philosophy here was strict retrieval grounding — responses had to be anchored to content retrieved from the vector database rather than the model's general pre-trained knowledge. This was a deliberate guardrail to ensure factual consistency and prevent hallucination, and it applied uniformly across both engineering and marketing prompts. We validated this constraint by testing an ungrounded variant (eng_ungrounded) that removed it, which caused BLEU to fall from 0.088 to 0.050 (−43%), confirming that this design lever is load-bearing (Please see 4.1).

Jargon Level determined how technical the language should be. Engineering prompts permitted domain-specific terminology and assumed familiarity with technical concepts. Marketing prompts dialed this back toward accessible, plain-language framing. While closely related to persona framing, jargon level was treated as an independent axis - because audience role and language complexity don't always move together, keeping them as separate levers gave finer control over the output.

The key difference between engineering and marketing prompts ultimately came down to persona framing and jargon level working in tandem: engineering prompts optimized for technical precision, while marketing prompts optimized for clarity and business relevance. The grounding constraint, however, remained consistent across both - the answer always had to come from the retrieved context, regardless of the audience.

QUESTION:

5.3.f. What type of limitations/risks would you see in using this system?

==== ENTER YOUR 5.3.f. ANSWER IN THIS TEXT BLOCK. Double click to open.

There are several limitations and risks to consider when deploying this system.

First, the LLM-as-judge metric exhibits a refusal penalty and helpfulness bias. When the retrieved context does not contain enough information to answer faithfully, a well-grounded model should refuse — but the judge rewards models that attempt a helpful-sounding response regardless of grounding. For example, the ungrounded prompt variant (eng_ungrounded) scored higher on the judge (4.16) than the grounded baseline eng_v1 (3.44), despite producing less faithful answers, because removing the grounding constraint allowed the model to synthesize from pre-trained knowledge rather than retrieved content. Relying on the judge alone for production monitoring would silently approve lower-quality answers; monitoring should include BLEU and semantic similarity, or human spot-checks, alongside the judge.

Second, the corpus is static. Our current RAG system draws from a fixed set of documents ingested at build time, with no mechanism for periodic updates. To keep the system current, we would need to implement scheduled re-ingestion — whether from internal company databases, new publications, or external sources. This design direction was not addressed in the current study and would be a necessary component of any production deployment.

Third, out-of-domain refusal reliability has limited validation. In earlier configurations before we identified the best setup, Q225 (which asks about Thanos rather than ML/AI topics) allowed the model to hallucinate an answer, when the correct behavior is to refuse because the vector database contains no such information. Our current best config handles Q225 correctly with a graceful refusal, but we only probed out-of-domain behavior with 3 of 30 test questions. With 90% of the test set being in-domain, we have limited evidence about refusal reliability across a broader distribution of off-topic queries. This capability needs further validation before production deployment.

Fourth, chunk size presents an inherent trade-off with no single optimal value. At chunk_size=50, context is too fragmented for the model to construct coherent answers. Increasing chunk size addresses this, but at chunk_size=5000, BLEU drops 14% relative to our best config and generation time increases 3.5× (~28 seconds per query versus ~8 seconds). A potential improvement would be to triage queries by complexity: direct, fact-lookup questions could use smaller chunk sizes (256–512) for faster, more precise retrieval, while multi-hop reasoning questions that require broader context could use larger chunk sizes (1,000–5,000). This adaptive chunking strategy would need to be tailored per user group and validated to confirm that the quality difference justifies the added system complexity.

Fifth, the blind test (30 held-out questions with no gold answers) validated system robustness but also revealed that refusal quality can vary with prompt formatting. The system handles out-of-domain queries correctly: both Q117 (mammalian brain KG triples) and Q225 (Thanos/Deadpool actors) were refused by both personas in the notebook’s current configuration, producing clean refusals with no fabricated details. However, in a separate blind test run using different prompt formatting (raw [INST] templates via /v1/completions), the Q225 marketing response cited actor names found incidentally in the retrieved arXiv context — names like Jacob Collins-Levy and Cillian Murphy that appeared as examples in unrelated WikiQA and faithfulness-evaluation passages — and misattributed them as relevant to the Thanos question. This is not hallucination from thin air but misattribution of retrieved content, and it demonstrates that prompt formatting affects refusal quality. Monitoring refusal quality (not just refusal rate) is necessary for production. Additionally, marketing responses are consistently shorter (mean ~614 characters vs ~1,221 for engineering), which follows our prompt design but means marketing users receive less detail per query.
